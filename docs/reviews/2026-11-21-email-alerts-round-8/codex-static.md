### Alert logic and delivery

**EAX-01.** The runner reads confirmed addresses once per organisation, copies the strings into an in-memory list, then sends sequentially. An Admin can delete an address and receive `204` **before the transition is claimed**, yet the later SMTP call still sends the screen and site names to that address. The removal dialog promises that alerts stop. Carry recipient IDs and revalidate the same confirmed row under its organisation immediately before SMTP handoff. Test removal of the second recipient while the first send is paused. [Queue construction](../../../apps/api/src/alerts.ts:189) · [SMTP handoff](../../../apps/api/src/alerts.ts:96) · [Removal](../../../apps/api/src/routes/alert-recipients.ts:153) · [Portal promise](../../../apps/portal/src/features/settings/AlertsPage.tsx:252)

**EAX-02.** The 14-day lookback is a **documented residual**. A screen open one hour a week can be configured with a 48-hour delay, but it can never accumulate 48 hours inside that window. The documented five-minute approximation has a second consequence. A valid daily opening of `09:01–09:04` UTC falls entirely between probes, so even the default 30-minute alert can remain silent indefinitely. Count actual open intervals in the site timezone until the threshold is reached. Cover both sparse weeks and openings between probe times. [Accepted hours](../../../packages/contracts/src/display.ts:43) · [Documented shortcuts](../../../docs/portal-v2/stage-c-alerts.md:124)

**EAX-03.** For a screen open `09:00–17:00`, a last report at `16:30` is below the 30-minute threshold at `16:59`. A check at `17:01` counts the earlier 30 open minutes and raises the alert while the screen is closed. The integration test keeps the screen closed for the *entire* interval. Require the screen to be open at the time of an offline claim, preserving accumulated minutes for its next opening. [DEC-37 working-hours decision](../../../docs/portal-v2/stage-c-alerts.md:14) · [Existing test](../../../tests/integration/display-alerts.test.ts:128)

**EAX-04.** An episode stores the stale report time and display ID. If a replacement player sends its first heartbeat before the next check, its newer timestamp satisfies the recovery condition. The runner sends and audits “reporting again,” although the spec requires silent closure on re-pair. Associate the episode with the originating registration, or close it transactionally on replacement. Extend the test to send the new player’s heartbeat *before* checking. [Episode schema](../../../db/migrations/0014_display_alerts.sql:45) · [Silent-close requirement](../../../docs/portal-v2/stage-c-alerts.md:47) · [Existing test order](../../../tests/integration/display-alerts.test.ts:149)

**EAX-05.** The opening `INSERT` rechecks the heartbeat timestamp only. If an Editor turns alerts off, or an operator revokes the registration after the candidate read and before the claim, that timestamp can still match. The closing `DELETE` likewise uses an earlier back-online preference. Revalidate the active registration and relevant settings at the claim, with a consistent locking order. Add a test that commits the settings change or revocation between selection and claim. [Candidate read](../../../apps/api/src/alerts.ts:157) · [Closing claim](../../../apps/api/src/alerts.ts:220) · [Revocation leaves the delivery row in place](../../../apps/api/src/routes/displays.ts:691)

**EAX-06.** The lock connection’s error handler sets `broken`, which is used when releasing the client. The loop continues using other pooled connections and continues sending. A second runner can acquire the released lock and send recovery to a recipient before the first runner hands that recipient the older offline message. Stop claiming and starting sends when lock ownership is lost, and report the interrupted run as failed. The existing concurrency test exercises a healthy lock. This failure also applies to a direct database connection.
