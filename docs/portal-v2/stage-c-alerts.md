# Portal v2, stage C: e-mail alerts for screens (CMS-15 build spec)

Date: 2026-11-21. Card CMS-15, decision DEC-37 (`docs/decisions-2026-11.md`). Branch `feat/cms-15-email-alerts`. Builds on CMS-13 (roles, DEC-35) and follows the same rules: `docs/portal-v2/stage-c.md` (conventions, sections 1 and 6), AGENTS.md (review rules), and the ponytail rule: the least new code that does the whole job, and every known limit gets `// shortcut: <limit>, <when to upgrade>`.

**What it delivers.** An e-mail when a screen has stopped reporting for longer than its offline delay, and another when it reports again. Each organisation keeps one list of alert addresses; an address receives nothing until its owner confirms it from a link. Every alert goes to every confirmed address of the screen's organisation.

**Decisions (Michael, 2026-11-21, all four recommended options):**

| # | Question | Answer |
|---|---|---|
| A1 | Who receives alerts | One alert address list per organisation, for all screens. Each address is confirmed by its owner first (DEC-29; record D3 a). No member e-mail is stored (DEC-35 unchanged). |
| A2 | Who changes what | A screen's alert settings: Editor and up (new key `screen.alerts`). The address list: Admin and up (new key `alerts.manage`), because adding an outside address collects personal data. |
| A3 | Defaults | Every screen, existing and new: offline e-mail after 30 minutes, back-online e-mail on (mvp-spec section 13). Nothing is sent until an address is confirmed. |
| A4 | Working hours | The offline delay counts only while the screen is inside its working hours. A screen switched off every night does not alert at night, and does not alert at opening time if it reports within the delay. |

**Not in this build** (named, not built): per-screen recipient choice; temperature, storage, update-failed and delivery-error alerts (mvp-spec section 13); SMS; an unsubscribe link (the footer says who to ask; see section 8); resending a confirmation (remove and add again); TINNOX staff as recipients (no staff in customer accounts before H1); HTML e-mail; alert history page (the audit log is the history).

## 1. Model in six sentences

A display has `alert_offline_minutes` (NULL means off; else 30 to 2880 in steps of 30) and `alert_back_online`. A check runs about every minute: for each organisation it reads, under RLS, every paired display whose latest report comes from its active registration, and compares the report time with the delay, counting only time inside working hours. The first run that finds a display over its delay claims it by writing `display_alert.offline_since` (the stale report time) in a conditional statement, writes a `system` audit row in the same transaction, commits, then sends one e-mail to every confirmed address. A later run that finds a report newer than `offline_since` clears it the same way and, if `alert_back_online` is on, sends the back-online e-mail. Claims make a second runner (another API instance, the one-shot command) harmless; a session advisory lock makes it skip early. Sending happens after commit, so delivery is at most once per transition.

## 2. Migration `db/migrations/0014_display_alerts.sql`

- `display`: `ADD COLUMN alert_offline_minutes integer DEFAULT 30 CHECK (alert_offline_minutes IS NULL OR (alert_offline_minutes BETWEEN 30 AND 2880 AND alert_offline_minutes % 30 = 0))`, `ADD COLUMN alert_back_online boolean NOT NULL DEFAULT true`. Constant defaults: no table rewrite. `GRANT UPDATE (alert_offline_minutes, alert_back_online) ON public.display TO tinnox_app`.
- `display_alert` (open offline episode per display): `display_id uuid PRIMARY KEY`, `org_id uuid NOT NULL`, `offline_since timestamptz NOT NULL` (the report time that went stale), `notified_at timestamptz NOT NULL DEFAULT now()`; FK `(display_id, org_id) REFERENCES display (id, org_id)`. A row exists only while an offline e-mail is open; it is deleted when the screen reports again or stops being eligible. `tinnox_app`: SELECT, INSERT, DELETE.
- `alert_recipient`: `id uuid PK DEFAULT gen_random_uuid()`, `org_id uuid NOT NULL REFERENCES organization`, `email text NOT NULL` (lower-cased by the API; CHECK length 3 to 254), `created_at timestamptz NOT NULL DEFAULT now()`, `created_by uuid` (membership id, composite FK `(created_by, org_id)` to membership), `confirmed_at timestamptz`, `confirm_token_hash bytea` (SHA-256; NULL once confirmed), `confirm_expires_at timestamptz`; `UNIQUE (org_id, email)`, `UNIQUE (id, org_id)`; CHECK: confirmed rows have no token, unconfirmed rows have token and expiry. At most 20 per organisation (count under a per-organisation advisory lock, as tags). `tinnox_app`: SELECT, INSERT, DELETE, `UPDATE (confirmed_at, confirm_token_hash, confirm_expires_at)`.
- Both tables: ENABLE and FORCE RLS, policy `tenant_isolation` on `org_id = public.app_org_id()` (the 0001 loop pattern).
- `sec.alert_recipient_by_token_hash(p_hash bytea) RETURNS TABLE (org_id uuid, recipient_id uuid)`: the only new cross-organisation read. Justification: the confirmation link is opened by someone with no session, so the organisation is unknown until the token is found. Returns the minimum, only for an unexpired unconfirmed row. Column grant `SELECT (id, org_id, confirm_token_hash, confirm_expires_at, confirmed_at) ON alert_recipient TO tinnox_definer`. Created under `SET LOCAL ROLE tinnox_definer`, `SECURITY DEFINER SET search_path = pg_catalog, pg_temp`, EXECUTE to `tinnox_app` only, plus the trailing guard block.
- The check needs no `sec.*` function: it lists organisations through the existing grant (see section 4).

## 4. API (`apps/api`)

- **Mail** (`src/mail.ts`): `createMailer(config)` returns `send({ to, subject, text })` built on `nodemailer` SMTP, or `null` when `SMTP_HOST` is unset. Config (all optional): `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_SECURE` (implicit TLS), `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` (required when `SMTP_HOST` is set). Production refuses a development-looking password and plaintext SMTP to a non-loopback host. Plain text only. Never log addresses, tokens or transport options. `AppContext.mail` holds the sender (tests inject a stub).
- **Check** (`src/alerts.ts`): `runDisplayAlerts({ pool, now, mail, portalOrigin, limits })` returns counts `{ skipped, offline, online, closed, failed }`, shaped like `runHousekeeping`.
  1. Take `pg_try_advisory_lock(hashtextextended('tinnox.display_alerts', 0))` on one dedicated pooled client (no transaction open, so pool timeouts do not apply); if false return `skipped`. Unlock and release in `finally`.
  2. List organisations (`SELECT id FROM organization` through `withoutOrg`/`poolAsTx` only if the existing grants allow it; otherwise a `sec.*` function returning ids only).
  3. Per organisation, in `withOrg`: read displays (`loadStatusViews`-style join: active registration, `display_delivery.reporting_registration_id = active id`, `last_heartbeat_at`, site time zone, working hours, alert settings) with `display_alert`, and confirmed recipients. Decide in code with `offlineDue`. Claim each transition with a conditional statement (`INSERT ... ON CONFLICT DO NOTHING RETURNING` to open; `DELETE ... WHERE offline_since = $seen RETURNING` to close), write `auditScoped` (`actorType: 'system'`) on the same transaction, commit.
  4. After commit, send one e-mail per confirmed recipient. A failed send is logged (no address) and counted; it is not retried (shortcut).
  - Close without e-mail when the display is no longer eligible: unpaired, re-paired and the new player has not reported yet, or alerts turned off. If the new player of a re-paired display has reported, the screen is reporting again, so the back-online e-mail is sent (section 9 row 22).
  - With no confirmed recipients the transition is still recorded (so a later confirmation does not send a stale alert).
- **Timer** (`src/main.ts`): when `ctx.mail` is set, a self-rescheduling `setTimeout` loop every 60 s (`unref`), started after listen, stopped and awaited before `pool.end()`. Without mail: one warning at start-up.
- **One-shot command** (`src/alerts-once.ts`, `npm run alerts:once -w @tinnox/api`): loads config, runs the check once, exits non-zero on failure. For a cloud scheduler after deployment.
- **Routes**:
  - `PATCH /api/displays/:id` accepts `alertOfflineMinutes` and `alertBackOnline` (`DISPLAY_PATCH_KEYS` maps both to `screen.alerts`); audit `display.update` with the changed field names.
  - `GET /api/alert-recipients` (`alerts.manage`).
  - `POST /api/alert-recipients` `{ email }` (`alerts.manage`): validate with `InviteEmailSchema`, lower-case, insert with a token hash and 7-day expiry, audit `alert_recipient.add`, commit, send the confirmation e-mail. 409 if already listed; 503 if mail is not configured (nothing inserted).
  - `DELETE /api/alert-recipients/:id` (`alerts.manage`): audit `alert_recipient.remove`.
  - `POST /api/alert-recipients/confirm` `{ token }`: public (no session, not in `ROUTE_PERMISSIONS`'s operator set; rate-limited per address). `withResolvedOrg`: `sec.alert_recipient_by_token_hash`, enter the organisation, conditional `UPDATE ... SET confirmed_at = now(), confirm_token_hash = NULL, confirm_expires_at = NULL ... RETURNING`, audit `alert_recipient.confirm` (`actorType: 'anonymous'`). Unknown, used and expired tokens all get the same 404.
  - Writes use `withOrgAllowed` and the `writeLimit` rate limit, as members.ts.
- **Audit actions** (category `alert_recipient` for the list; screen alerts under `display`): `display.offline_alert`, `display.online_alert` (detail `{ recipients: <count> }`, never addresses), `alert_recipient.add`, `alert_recipient.remove`, `alert_recipient.confirm` (object = recipient id; never the address). Portal wording for each in `activity.ts`/`auditView.ts`.

## 5. E-mails (plain text)

- **Offline.** Subject `Screen not reporting: <screen name>`. Body: the screen name, site, organisation, "Last report: <time in the site's time zone>", "This alert was sent because the screen has not reported for <delay>.", a link to the screen page (`<portal origin>/screens/<id>`, no token), and the footer.
- **Back online.** Subject `Screen reporting again: <screen name>`. Body: the name, site, the time it reported again, the link, the footer.
- **Confirmation.** Subject `Confirm alert e-mails from TINNOX CMS`. Body: who added it is not named; "<organisation> asked to send screen alerts to this address. To agree, open this link within 7 days: <portal origin>/alerts/confirm#<token>. If you did not expect this, ignore this e-mail and nothing more will be sent."
- **Footer.** "You receive this because this address is on the alert list of <organisation> in TINNOX CMS. To stop, ask an Admin of that organisation to remove it."
- Wording says "not reporting", never "offline because…" or "online" (DEC-33 honesty rule).

**Shortcuts** (each has a `// shortcut:` comment in the code):

- `offlineDue` scans at most the last 14 days (4032 steps, about 10 ms for one screen); a delay that needs more working hours than that fires at the first open moment after 14 silent days instead.
- An alert that comes due in the last minute before closing is sent just after closing (the check runs about once a minute; Michael kept this in round 8, EAX-03).
- The check reads each organisation's alert settings and active registrations once per run; a change that commits during the run (alerts off, a revocation) applies from the next run, which closes the episode silently, so at most one e-mail goes out on the old settings.
- E-mails are sent one at a time and a failed send is not retried.
- One query per organisation reads every display.
- `sec.display_alert_orgs` returns every organisation on each run.
- The Settings → Alerts list is not paged or searched (at most 20 addresses).

**Report time precision:** the check reads, compares and stores report times truncated to milliseconds in SQL (`date_trunc('milliseconds', last_heartbeat_at)`), the precision of the JavaScript `Date` it compares with, so a report time with microseconds (written by SQL `now()` or any other writer) is claimed and its episode closes (integration case "claims and closes a report time with microseconds").

**Not verified yet:** a real provider's TLS (SES, STARTTLS with credentials); several API instances at once (the lock is tested with concurrent calls in one process; the conditional claims are not raced); behaviour behind a pooler that breaks session advisory locks (transaction-mode PgBouncer, RDS Proxy); a screen-reader pass of the new pages. The styleguide demo (`features/styleguide/FormSections.tsx`) still shows a disabled "Alerts" tab (demo only).

**Open for TINNOX:** whether the Spam Act needs an unsubscribe link in alert e-mails (operations checklist section 5, item 16); the e-mail provider review (SES in Sydney planned; section 4); whether expired unconfirmed addresses are deleted after a period (section 3).
