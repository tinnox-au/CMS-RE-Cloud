# Threat model: TINNOX CMS prototype M0

Date: 2026-11-14. Written against the design in `docs/prototype-m0.md` (decisions D1 to D19 and the section 9 deviations) and `docs/dev-handoff.md` before the API, portal and player existed, then **revised against the built system by the integration step on 2026-11-14** (section 8).

**Status of the mitigations:** the "Design mitigation" column below is the design as first written. Section 8 records where the build differs and which mitigations are implemented and tested; the evidence for each control (test names, commands and results) is in `docs/security/control-matrix.md` and `docs/prototype-validation.md`. Where section 8 and the table disagree, section 8 describes the system as built.

This is an internal engineering prototype with synthetic data. It is not certified, not assessed, and not a statement of legal compliance.

## 1. Assets

| # | Asset | Why it matters |
|---|---|---|
| A1 | Organisation data: displays, playlists, publications, delivery state | Confidentiality and integrity per organisation; wrong content on a public screen is the main business harm |
| A2 | Media files (images, video) under `MEDIA_ROOT` | Private until published to a display; may be commercially sensitive before a campaign |
| A3 | Member identity and session (Keycloak account, session cookie, CSRF token) | Grants what the member's role allows in one organisation |
| A4 | Device token (per player registration) | Grants manifest and media of one display |
| A5 | Pairing code and polling token | Short-lived path to obtaining A4 |
| A6 | Server secrets: `SESSION_SECRET`, `MEDIA_URL_HMAC_SECRET`, `PAIRING_CLIENT_KEY_SECRET`, `OIDC_CLIENT_SECRET`, database role passwords | Forging signed URLs, sessions or database access |
| A7 | Audit trail (`audit_event`) | Evidence after an incident |
| A8 | What is shown on the screen | Integrity and availability of the published content |
| A9 | Source, dependencies and build pipeline | A compromise reaches every other asset |

Personal information held is small: the member's OIDC subject, their display name (`membership.display_name`, kept for removed members so old activity stays readable), the name and work e-mail address of a person invited while the invite is pending (deleted when it closes), the hashed client address used for pairing rate limits, member identifiers in audit rows, and (CMS-15) the organisation's alert e-mail addresses, which may belong to people outside it (kept until an Admin removes them; section 15). ID tokens carry no name claims. Media is synthetic in M0; real customer media could contain personal information (images of people), which TINNOX must consider before external use.

## 2. Actors

| Actor | Trust | Notes |
|---|---|---|
| Member (Owner, Admin, Editor or Viewer) | Authenticated, authorised for one organisation within their role (DEC-35) | May make mistakes; may be phished |

| Operator of another organisation | Authenticated, hostile to this organisation's data | The main isolation test case |
| Anonymous internet client | None | Can reach `POST /player/pairing`, login redirects, health endpoints |
| Registered player | Untrusted client holding A4 | Its reports are evidence from software, never authority for operator actions |
| Person with physical or local access to a player device | None | Can read browser storage, clone the profile |
| Uploaded file | Hostile input | May target the image or video parser |
| Developer and CI | Trusted, but accounts and dependencies can be compromised | |
| Database administrator / host administrator | Trusted with residual access | Can bypass row-level security and triggers |
| E-mail provider (SMTP) and alert recipients' mailboxes | Outside TINNOX's control | Receive screen, site and organisation names and the confirmation link (CMS-15, section 15); Mailpit on 127.0.0.1 in development |
| Future: LED controller and vendor software | Untrusted until verified per model | Not connected in M0 |

## 3. Trust boundaries

1. **Operator browser to portal and API.** Cookie session over the portal origin; the portal proxies `/api` (D5, D7). Boundary controls: OIDC login, session cookie flags, CSRF token and Origin check (D6), CSP (D18), schema validation (D2).
2. **API to identity provider (Keycloak).** Back-channel code exchange with PKCE; the API trusts signed ID tokens from the configured issuer only (D5). The identity provider owns passwords and TOTP.
3. **API to PostgreSQL.** The runtime role `tinnox_app` is not owner, not superuser, `NOBYPASSRLS`; tenant context is transaction-scoped (D3, D4). Pre-tenant lookups cross through `sec.*` `SECURITY DEFINER` functions owned by `tinnox_definer` (section 9 deviation).
4. **API to media worker and storage.** Untrusted bytes cross into an isolated container through a shared jobs directory only; the worker has no network and no secrets, and its verdict is data the API validates (D11). Accepted files move to private storage with server-generated keys (D10).
5. **Player browser to API.** Separate origin, bearer device token, CORS limited to the player origin (D7, D8, D13). Everything the player sends is untrusted.
6. **Pairing flow.** An unauthenticated player and an authenticated operator meet through a short code; the device token travels only to the holder of the polling token (D9).
7. **Organisation boundary.** Every row carries `org_id`; the organisation comes only from the membership of the verified identity or from the device credential, never from a submitted identifier (D3, D4, D5).
8. **Future controller boundary (not built).** Behind the delivery port (D15). Content delivery is separate from controller commands; no controller command exists in M0. Any adapter, vendor API, credential or vendor cloud needs its own threat model and data-flow review before it is connected (`docs/hardware-next-step.md`).
9. **Development and build boundary.** npm registry, container registries and GitHub Actions are build-time services, separate from run-time data flows (D1, D18).

## 4. Data flows

1. **Sign-in.** Browser → `GET /api/auth/login` → redirect to Keycloak (state, nonce, PKCE challenge; verifier kept server-side in `login_state`) → password and TOTP at Keycloak → `GET /api/auth/callback` → API exchanges the code, verifies the ID token, looks up `membership` by `sub` (a removed member is ignored), compares the ID token's `auth_time` with the member's cut-off (`sessions_valid_after`; too old → one more round at the provider with `prompt=login`), creates a `session` row (only a hash of the session id stored) and records `first_signed_in_at` once → opaque `HttpOnly` cookie. Tokens stay on the server.
2. **Member actions.** Browser → `/api/*` with cookie and `X-CSRF-Token` → session lookup → permission preHandler (the route's keys against the session's role, before any lookup) → `withOrg(orgId)`; a write first runs `assertStillAllowed` (the member row again, `FOR SHARE`) → SQL under row-level security → audit row.
3. **Upload.** Browser → `POST /api/media` (multipart, streamed, byte limit enforced while receiving) → API writes `inbox/<jobId>` and `inbox/<jobId>.json` → worker inspects (magic bytes, `sharp`, `ffprobe` with timeout) → `outbox/<jobId>.json` → API validates the result, computes SHA-256 and size itself, moves the file into storage, sets `ready` or `failed`.
4. **Pairing.** Player → `POST /player/pairing` (rate-limited) → code and polling token → operator types the code into `POST /api/displays/:id/claim` → player polls `GET /player/pairing/:id` with the polling token → device token returned once; only its hash is stored.
5. **Publish.** Operator → `POST /api/playlists/:id/publish` with `Idempotency-Key` → capability check for the display's route → immutable `publication` row and `publication_asset` rows → `display_delivery.desired_publication_id`.
6. **Delivery.** Player → `GET /player/manifest` (bearer token, ETag) → `POST /player/media-urls` → `GET /player/media/:assetId?...&exp=&sig=` (HMAC-signed, short-lived, bound to the registration) → player verifies size and SHA-256, stages, activates atomically.
7. **Status.** Player → `POST /player/heartbeat` (`seq`, states, errors) → validated, reduced into `display_delivery` → portal reads `GET /api/displays/:id/status`.
8. **Invite (stage C).** An Owner or Admin → `POST /api/invites` (name, work e-mail, role, within the rank rule) → pending `member_invite` → TINNOX staff run `provision-member pending` daily and `fulfil` on a controlled host after confirming the person with the requester → the identity-provider account is read (`tinnox-provisioning` client, `view-users`), the membership is created and the invite's name and e-mail are deleted → the person's first sign-in sets `first_signed_in_at`.

9. **E-mail alerts (CMS-15).** The API's alert check (every minute, or `alerts:once`) → SMTP to the configured provider → each confirmed address. An Admin adds an address → confirmation e-mail with a link whose token is in the fragment → the owner's browser posts it to `POST /api/alert-recipients/confirm` (no session). Section 15.

Apart from the e-mail of flow 9 (sent to Mailpit on 127.0.0.1 in development), no flow in M0 leaves the local machine at run time. No analytics, remote fonts, CDN or error-reporting service is called (D18).

## 6. Stated limits of this model

- Revocation stops future API and media access. It cannot erase content from a device that is offline or already holds a cache.
- A player report is evidence from software. It is not proof that a physical screen shows the content.
- The model covers the local prototype. Hosting, network, TLS termination, key management, backup storage and support access for a real deployment are not designed here and need their own review.
- Availability beyond one process on one machine is out of scope for M0.
- The future controller boundary is described, not analysed. No statement here covers NovaStar or Huidu equipment.

## 7. Review triggers

Revise this page when: a new route, role or external service is added; the identity provider changes; any controller adapter or vendor API is introduced; before any external customer use.

## 9. After the review fixes (2026-11-14)

Three reviewers examined the integrated prototype. Their findings and the fixes are listed in `docs/prototype-validation.md` section 10. Changes to the picture in sections 5 and 8:

| Threat | Change |
|---|---|
| T1 | A job whose inspection was interrupted is tried once more; a file that kills the worker twice is rejected (tested with the real worker container and crash markers, not with a killed process). `ffmpeg` in the worker image is pinned to `8.1.3-r0`. Orphaned quarantine files are swept at start-up and hourly. Still open: the quarantine is readable by every local user and the outbox is world-writable on Linux (`0755`/`0644`, `1777`), so a local process could read pending uploads or forge a verdict; the API re-checks magic bytes, SHA-256 and limits but not the content. | T7, T15 | A player could grow `heartbeat_log` without bound (ignored reports were stored and pruning depended on its own `seq`). | T8, T15 | Anyone could send invented bearer tokens to the credentialed player routes: each got a fresh rate-limit bucket (keyed by the header) and wrote one unscoped audit row, without limit. Failed lookups are now counted per client address (IPv6 per /64): after 30 in 10 minutes the address gets `429` before any database lookup, except for a credential that was verified recently, and the audit trail gets one row when an address starts failing and one when it is throttled. In memory, per process; a distributed source is not limited. |
| T11 | Keycloak's default browser flow ran the one-time-code step only for users who already had an authenticator, so a user without one (new, or one who removed it) signed in with a password only, and the API accepted it in development. | T12 | ID tokens carry no names (the client has no `profile` scope) and the stored copy is removed when the session ends. Audit `occurred_at` is set by the database on every insert. Rejected device credentials are audited per client address with a keyed fingerprint of the address, not per token. |
| T13 | Build-time sources were incomplete: ghcr.io (gitleaks image), the Alpine package repository (`ffmpeg`) and Playwright's browser download are now in the inventory (operations checklist section 4). |

## 11. Stage B, slice 3: schedules (2026-11-17)

A schedule is a default playlist plus weekly events that name other playlists; a screen has a playlist or a schedule assigned. A push copies every playlist of the schedule into one immutable publication (manifest v4), and the player picks between them from its own corrected clock. Spec: `docs/portal-v2/stage-b.md`, slice 3. No new dependency, no new route outside the operator scope, no change to the player routes, the signed media URLs or the heartbeat.

| Threat | Change |
|---|---|
| T2, T5 | Schedules add no outside data: a schedule refers only to playlists of its own organisation, nothing is fetched, and no new content type reaches a screen. The two new tables, `schedule` and `schedule_event`, have forced row-level security and the tenant policy, organisation-scoped foreign keys (to `playlist`, and from `display.assigned_schedule_id`), no `UPDATE` grant on a schedule's `id` or `org_id`, and no `UPDATE` grant at all on `schedule_event`; the five `/api/schedules` routes sit behind the session, CSRF and exact-Origin checks like every operator route. A schedule's name and description are operator text: validated by the strict contracts (as playlist names are) and shown in the portal as text nodes only (React escaping; no `innerHTML`). They are not copied into the manifest, which holds no schedule or playlist name or id, so they never reach a player. Media of every playlist of a pushed schedule is authorised through the same `publication_asset` rows as before. Residual, availability only: a player build older than 0.4.0 that is sent a v4 manifest refuses it and then asks for the manifest and sends a heartbeat about every 2 seconds until its page is reloaded (both under the per-credential route limits); the release note says to reload screens first, and 0.4.0 no longer does this for a later version. |

## 14. Stage C: roles and people (2026-11-20)

Four nested roles, one per person: Owner, Admin, Editor and Viewer (DEC-35). Owners and Admins see the Users page, request invites that TINNOX completes, change roles within the rank rule, correct names, sign people out everywhere and remove them. Spec: `docs/portal-v2/stage-c.md`; decision record: `docs/portal-v2/stage-c-roles-decision.md`; review: `docs/reviews/2026-11-20-stage-c-review/`. Migration 0013 adds `member_invite` (forced row-level security, the tenant policy, composite foreign keys) and the membership columns; the eight people routes sit behind the session, CSRF and exact-Origin checks like every operator route, and another organisation's member or invite id is answered as an unknown id (404).

| Threat | Change |
|---|---|
| T17 (new) | Escalation inside an organisation: mitigations and residuals in the table above, evidence in control matrix B16. |
| T2 | A refusal by role is the same 403 for every id and is decided before the row is read, so it confirms nothing about another organisation's ids; 404 stays the answer once the role allows the route. `tinnox_definer` gains a script-only cross-organisation read of `member_invite` (names and work e-mail addresses of pending invites) and `UPDATE (status)`; no `sec.*` function reads it and `tinnox_app` cannot reach it. |
| T3 | Editors, Admins and Owners pair; each has a wrong-code budget, so more members with `screen.pair` allow more guesses. Ending a member's sessions closes the claim window: `sec.pairing_complete` refuses a claim whose claimer was removed, and (round 6, RCX-01) a claim made at or before the claimer's cut-off. So a claim made before a removal, a demotion or a sign-out everywhere cannot be collected, also after a reactivation, which keeps the cut-off. Such a pairing is expired without its own audit row. |
| T10, T11 | "Sign out everywhere", removal, demotion and `provision-member mfa-reset` set the member's cut-off. A browser still signed in at Keycloak must enter the password and one-time code again (`prompt=login`, `auth_time` compared with the cut-off). `auth_time` is the provider's clock and the cut-off the database's, so a provider clock running ahead lets a slightly older sign-in through; hosts need synchronised time. `npm run verify:oidc` confirmed Keycloak's behaviour against a recreated realm on 2026-11-20; Cognito's `auth_time` and `prompt=login` are unverified (A3). |
| T12 | Audit rows carry ids, never names or e-mail addresses; names come from `membership` when the log is read. A sign-in that waits past the lock timeout for the member row is recorded as an unscoped `auth.login` failure (`member_locked`). Migration 0013's role mapping writes no audit row (nothing about membership was audited before it). |
| T14 | Routine provisioning runs as `tinnox_migrator` from a controlled host, with its read of every organisation's invite queue under `SET LOCAL ROLE tinnox_definer`; staff ids are typed, not proven. The development `.env` holds the migrator URL and the provisioning reader secret, and the development API loads the whole file; a production start-up check is deferred. |

## 15. CMS-15: e-mail alerts (2026-11-21)

An e-mail goes to every confirmed alert address of the organisation when a screen has not reported for longer than its offline delay, counted inside its working hours, and another when it reports again (DEC-37). Spec and as built: `docs/portal-v2/stage-c-alerts.md`. Migration 0014 adds `display_alert` and `alert_recipient` (forced row-level security, the tenant policy, composite foreign keys), two display columns and two `sec.*` functions. The three `/api/alert-recipients` routes need `alerts.manage` (Admin and up) and sit behind the session, CSRF and exact-Origin checks; `POST /api/alert-recipients/confirm` is the only public write. SMTP is the first run-time flow that leaves the machine (flow 9).

| Threat | Change |
|---|---|
| T2 | Two new cross-organisation reads, both justified in the 0014 header. `sec.display_alert_orgs()` returns organisation ids only: the check has no session, and every read of tenant data then happens in `withOrg`, one organisation at a time, so an e-mail names only that organisation's screens and goes only to its confirmed addresses. `sec.alert_recipient_by_token_hash(bytea)` returns the organisation and recipient id of an unexpired, unconfirmed row, never the address; `tinnox_definer` reads five `alert_recipient` columns, not `email`. Another organisation's recipient id answers 404. Residual: `sec.display_alert_orgs` lists every organisation on each run (a shortcut until there are many). |
| T6 | The confirm route takes no session and no CSRF token; the portal's API client exempts exactly that path. It can only confirm the one row its token names: 32 random bytes, stored as SHA-256, valid 7 days, used once. Unknown, used and expired tokens get the same 404; 10 attempts per minute per client address. The token is in the link's fragment, so it never reaches a server log, and the confirm page removes it from the address bar. Residual: a mail scanner that runs the page's script would confirm the address (a scanner that only fetches the link does not). |
| T12 | E-mails carry the screen, site and organisation names, the last report time in the site's zone and a link to the screen page, with no token, signed URL, content or credential. Alert audit rows carry the recipient count; recipient audit rows carry the recipient id, never the address. Neither the mailer nor the check logs an address, a token, the transport options or the server's reply. Residual: those names travel in clear to the mail provider and to every recipient's mailbox, outside TINNOX's control. |
| T15 | An Admin can add a stranger's address: the stranger receives one confirmation e-mail naming the organisation, and nothing more unless they confirm. At most 20 addresses per organisation. Each write route (add, remove) allows 30 requests per minute per client address, per API process, in memory (`@fastify/rate-limit` keyed on the client address, not the member): members behind one address share a budget, and one Admin using several addresses or several API instances gets several. Residual: removing and adding the same address again sends another confirmation, bounded only by that limit, so about 30 confirmations a minute per client address and process to one stranger; every add is audited with the actor. There is no per-address or per-organisation cap on confirmation e-mails. There is no unsubscribe link: the footer says to ask an Admin of the organisation (Spam Act question open, operations checklist section 5). |
| T16 | SMTP settings come from the environment. STARTTLS is required in every mode to any host but loopback (`requireTLS`), or implicit TLS with `SMTP_SECURE=true`; production refuses a development or placeholder `SMTP_PASSWORD`. The SMTP password is a new server secret (A6). Residual: the provider's certificate is checked with Node's default trust store, not pinned. |
| T13 | New run-time dependency `nodemailer` 10.3.1 (MIT-0, no dependencies), pinned exactly in `apps/api/package.json`. Development adds the Mailpit v1.33.0 image, pinned by digest, bound to 127.0.0.1, with its version check off. |
| T7, T14 | Alerts are evidence of missing reports, not of a dark screen: a compromised player can keep reporting and so suppress its own alert, and the e-mails say "not reporting", never "offline" (DEC-33). Delivery is at most once per transition: the claim and its audit row commit before the e-mail goes out, and a failed send is logged and counted, not retried, so a crash or an SMTP outage at that moment loses that e-mail. Several runners (API instances, `alerts:once`) are harmless: a session advisory lock makes a second run skip and each transition is claimed by a conditional statement. A run that is shutting down stops claiming before its next organisation, and the e-mails it has claimed get the shutdown budget. Residual: behind a transaction-mode pooler the session lock is unreliable. The claims still prevent duplicates, but the lock and its unlock can land on different server connections, so the lock can stay held on a connection and later runs skip: alerts become intermittent or stop until that connection closes. An unlock that answers false destroys the run's connection, and the API logs a warning at every fifth skipped run in a row, so this is visible, not silent. |
