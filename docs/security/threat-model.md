# Threat model: TINNOX CMS prototype M0

Date: 2026-11-14. Written against the design in `docs/prototype-m0.md` (decisions D1 to D19 and the section 9 deviations) and `docs/dev-handoff.md` before the API, portal and player existed, then **revised against the built system by the integration step on 2026-11-14** (section 8).

**Status of the mitigations:** the "Design mitigation" column below is the design as first written. Section 8 records where the build differs and which mitigations are implemented and tested; the evidence for each control (test names, commands and results) is in `docs/security/control-matrix.md` and `docs/prototype-validation.md`. Where section 8 and the table disagree, section 8 describes the system as built.

This is an internal engineering prototype with synthetic data. It is not certified, not assessed, and not a statement of legal compliance.

## 1. Assets

| # | Asset | Why it matters |
|---|---|---|
| A1 | Organisation data: displays, playlists, publications, delivery state | Confidentiality and integrity per organisation; wrong content on a public screen is the main business harm |
| A2 | Media files (images, video) under `MEDIA_ROOT` | Private until published to a display; may be commercially sensitive before a campaign |
| A3 | Operator identity and session (Keycloak account, session cookie, CSRF token) | Grants every operator action for the organisation |
| A4 | Device token (per player registration) | Grants manifest and media of one display |
| A5 | Pairing code and polling token | Short-lived path to obtaining A4 |
| A6 | Server secrets: `SESSION_SECRET`, `MEDIA_URL_HMAC_SECRET`, `PAIRING_CLIENT_KEY_SECRET`, `OIDC_CLIENT_SECRET`, database role passwords | Forging signed URLs, sessions or database access |
| A7 | Audit trail (`audit_event`) | Evidence after an incident |
| A8 | What is shown on the screen | Integrity and availability of the published content |
| A9 | Source, dependencies and build pipeline | A compromise reaches every other asset |

Personal information held in M0 is small: the operator's OIDC subject, username and name claims from the identity provider, the hashed client address used for pairing rate limits, and operator identifiers in audit rows. Media is synthetic in M0; real customer media could contain personal information (images of people), which TINNOX must consider before external use.

## 2. Actors

| Actor | Trust | Notes |
|---|---|---|
| Operator | Authenticated, authorised for one organisation | May make mistakes; may be phished |
| Operator of another organisation | Authenticated, hostile to this organisation's data | The main isolation test case |
| Anonymous internet client | None | Can reach `POST /player/pairing`, login redirects, health endpoints |
| Registered player | Untrusted client holding A4 | Its reports are evidence from software, never authority for operator actions |
| Person with physical or local access to a player device | None | Can read browser storage, clone the profile |
| Uploaded file | Hostile input | May target the image or video parser |
| Developer and CI | Trusted, but accounts and dependencies can be compromised | |
| Database administrator / host administrator | Trusted with residual access | Can bypass row-level security and triggers |
| Future: LED controller and vendor software | Untrusted until verified per model | Not connected in M0 |

## 3. Trust boundaries

1. **Operator browser to portal and API.** Cookie session over the portal origin; the portal proxies `/api` (D5, D7). Boundary controls: OIDC login, session cookie flags, CSRF token and Origin check (D6), CSP (D18), schema validation (D2).
2. **API to identity provider (Keycloak).** Back-channel code exchange with PKCE; the API trusts signed ID tokens from the configured issuer only (D5). The identity provider owns passwords and TOTP.
3. **API to PostgreSQL.** The runtime role `tinnox_app` is not owner, not superuser, `NOBYPASSRLS`; tenant context is transaction-scoped (D3, D4). Pre-tenant lookups cross through `sec.*` `SECURITY DEFINER` functions owned by `tinnox_definer` (section 9 deviation).
4. **API to media worker and storage.** Untrusted bytes cross into an isolated container through a shared jobs directory only; the worker has no network and no secrets, and its verdict is data the API validates (D11). Accepted files move to private storage with server-generated keys (D10).
5. **Player browser to API.** Separate origin, bearer device token, CORS limited to the player origin (D7, D8, D13). Everything the player sends is untrusted.
6. **Pairing flow.** An unauthenticated player and an authenticated operator meet through a short code; the device token travels only to the holder of the polling token (D9).
7. **Organisation boundary.** Every row carries `org_id`; the organisation comes only from the membership of the verified identity or from the device credential, never from a submitted identifier (D3, D4, D5).
8. **Future controller boundary (not built).** Behind the delivery port (D15). Content delivery is separate from controller commands; no controller command exists in M0. Any adapter, vendor API, credential or vendor cloud needs its own threat model and data-flow review before it is connected (`docs/hardware-next-step.md`).
9. **Development and build boundary.** npm registry, container registries and GitHub Actions are build-time services, separate from run-time data flows (D1, D18).

## 4. Data flows

1. **Sign-in.** Browser → `GET /api/auth/login` → redirect to Keycloak (state, nonce, PKCE challenge; verifier kept server-side in `login_state`) → password and TOTP at Keycloak → `GET /api/auth/callback` → API exchanges the code, verifies the ID token, looks up `membership` by `sub`, creates a `session` row (only a hash of the session id stored) → opaque `HttpOnly` cookie. Tokens stay on the server.
2. **Operator actions.** Browser → `/api/*` with cookie and `X-CSRF-Token` → session lookup → `withOrg(orgId)` → SQL under row-level security → audit row.
3. **Upload.** Browser → `POST /api/media` (multipart, streamed, byte limit enforced while receiving) → API writes `inbox/<jobId>` and `inbox/<jobId>.json` → worker inspects (magic bytes, `sharp`, `ffprobe` with timeout) → `outbox/<jobId>.json` → API validates the result, computes SHA-256 and size itself, moves the file into storage, sets `ready` or `failed`.
4. **Pairing.** Player → `POST /player/pairing` (rate-limited) → code and polling token → operator types the code into `POST /api/displays/:id/claim` → player polls `GET /player/pairing/:id` with the polling token → device token returned once; only its hash is stored.
5. **Publish.** Operator → `POST /api/playlists/:id/publish` with `Idempotency-Key` → capability check for the display's route → immutable `publication` row and `publication_asset` rows → `display_delivery.desired_publication_id`.
6. **Delivery.** Player → `GET /player/manifest` (bearer token, ETag) → `POST /player/media-urls` → `GET /player/media/:assetId?...&exp=&sig=` (HMAC-signed, short-lived, bound to the registration) → player verifies size and SHA-256, stages, activates atomically.
7. **Status.** Player → `POST /player/heartbeat` (`seq`, states, errors) → validated, reduced into `display_delivery` → portal reads `GET /api/displays/:id/status`.

No flow in M0 leaves the local machine at run time. No analytics, remote fonts, CDN or error-reporting service is called (D18).

## 6. Stated limits of this model

- Revocation stops future API and media access. It cannot erase content from a device that is offline or already holds a cache.
- A player report is evidence from software. It is not proof that a physical screen shows the content.
- The model covers the local prototype. Hosting, network, TLS termination, key management, backup storage and support access for a real deployment are not designed here and need their own review.
- Availability beyond one process on one machine is out of scope for M0.
- The future controller boundary is described, not analysed. No statement here covers NovaStar or Huidu equipment.

## 7. Review triggers

Revise this page when: a new route, role or external service is added; the identity provider changes; any controller adapter or vendor API is introduced; before any external customer use.

## 8. As built (integration review, 2026-11-14)

Every threat T1 to T16 has an implemented mitigation; the automated tests named in the control matrix exercise T1 to T11 and T13 to T16 directly. T12 (log leakage) was checked by searching the API log of a full end-to-end run. Differences from the design and points the table above does not show:

| Threat | As built |
|---|---|
| T1 | The API also checks the first bytes while receiving and refuses non-media content with 415 before anything is queued; the worker still inspects every accepted file. HEVC, VP9, 4:4:4 H.264, an over-limit image, a damaged JPEG, text, HTML and SVG were refused in tests with the real worker container. A real crash of the worker mid-inspection was not tested (timeouts and forged verdicts were). On macOS, Docker file sharing does not enforce the modes of the shared jobs directory; check on Linux before relying on them. Stage B slice 1 added image thumbnails with the checks and residual named in the T1 row; the other-uid case is not tested (it needs root to chown). |
| T2 | As designed. A second organisation with its own operator session and its own registered player was refused (404 or 401, never a confirming message) on every operator and player route with the first organisation's ids, through the API and in the browser; the runtime role sees nothing of another organisation without a `WHERE` clause. |
| T3 | As designed, with two attempt limits (5 wrong polling tokens lock a pairing session; 5 wrong codes per operator per 10 minutes) and a pairing-creation limit per client. The device token is created when the player collects it, so it never appears in the operator's request. |
| T4 | Signed media URLs use HMAC-SHA-256 over registration, publication, asset and expiry, and the registration is checked on every request, so revocation also kills unexpired URLs. New media URLs are issued only for the publication currently assigned to the display; an already issued URL stays valid for an asset of its own publication and display until it expires or the registration is revoked. Replayed callbacks, stale heartbeats and repeated publishes were tested. |
| T5 | The production builds of portal and player carry a strict CSP meta tag without inline script (the build fails otherwise); the Vite **development** server uses a looser CSP for hot reload. API responses carry `default-src 'none'`; media responses add `sandbox` and `nosniff`. No XSS payload test was written; containment rests on React escaping, the lint rules and CSP. |
| T6 | As designed: every state-changing `/api` route needs the session's CSRF token and the exact portal `Origin`; logout is a `POST` behind the same checks. Tested for missing and foreign values. |
| T7 | As designed. Clone behaviour (two contexts with one token) was not tested. |
| T8 | The device token is stored in clear in the player origin's IndexedDB. The player's own reset revokes its registration on the server (`DELETE /player/registration`) and removes the token and every cache; a revoked player removes them at its next contact. |
| T9 | Corrupt and interrupted downloads were tested in the browser (previous version kept, error reported, update completed after recovery). Storage-quota failure is tested only in player unit tests, not in a real browser. |
| T10 | Session id: 32 random bytes; only its SHA-256 is stored (not keyed; this row said "keyed hash" until the 2026-11-14 review corrected it); a new id at every sign-in; `HttpOnly`, `SameSite=Lax`, `Secure` with the `__Host-` prefix when the portal origin is https. |
| T11 | As designed. Production start-up also refuses to run unless `OIDC_MFA_ACR_VALUES` or `OIDC_MFA_AMR_VALUES` is set, so a production provider must expose MFA in its claims. |
| T12 | The API logs request paths without query strings and redacts credential headers and secret fields by name. After a full end-to-end run the API log contained no `sig=`, no bearer value, no session cookie and none of the generated passwords, TOTP secrets or server secrets. Unscoped audit events (failed sign-ins, pairing creation) are not visible through `GET /api/audit`. |
| T13 | GitHub Actions are pinned by commit SHA (checked against the release tags on 2026-11-14); the worker base image, PostgreSQL and Keycloak images are pinned by digest. `npm audit` reports 7 moderate advisories in development-only tooling. The CI workflow has never executed. |
| T14 | As designed. The backup exercise confirms the residual path: `pg_dump` must run as the PostgreSQL superuser, and a backup holds every organisation's data. |
| T15 | Rate limits are per route, per process, in memory (`@fastify/rate-limit`); the 200 MB upload limit is enforced in-stream (tested at a reduced limit); the per-organisation quota is enforced under concurrent uploads. |
| T16 | As designed and tested: the real API process refuses to start in production mode with the generated development configuration, and with a single development setting left. |

## 9. After the review fixes (2026-11-14)

Three reviewers examined the integrated prototype. Their findings and the fixes are listed in `docs/prototype-validation.md` section 10. Changes to the picture in sections 5 and 8:

| Threat | Change |
|---|---|
| T1 | A job whose inspection was interrupted is tried once more; a file that kills the worker twice is rejected (tested with the real worker container and crash markers, not with a killed process). `ffmpeg` in the worker image is pinned to `8.1.3-r0`. Orphaned quarantine files are swept at start-up and hourly. Still open: the quarantine is readable by every local user and the outbox is world-writable on Linux (`0755`/`0644`, `1777`), so a local process could read pending uploads or forge a verdict; the API re-checks magic bytes, SHA-256 and limits but not the content. A dedicated group shared by the API user and the worker uid is the intended fix. |
| T7, T15 | A player could grow `heartbeat_log` without bound (ignored reports were stored and pruning depended on its own `seq`). Now only accepted reports are stored, at most one per display per 10 s, and housekeeping deletes history older than `LIMIT_HEARTBEAT_LOG_RETENTION_HOURS` (default 24) across organisations through `sec.heartbeat_log_purge`. |
| T8, T15 | Anyone could send invented bearer tokens to the credentialed player routes: each got a fresh rate-limit bucket (keyed by the header) and wrote one unscoped audit row, without limit. Failed lookups are now counted per client address (IPv6 per /64): after 30 in 10 minutes the address gets `429` before any database lookup, except for a credential that was verified recently, and the audit trail gets one row when an address starts failing and one when it is throttled. In memory, per process; a distributed source is not limited. |
| T11 | Keycloak's default browser flow ran the one-time-code step only for users who already had an authenticator, so a user without one (new, or one who removed it) signed in with a password only, and the API accepted it in development. The realm template now binds the `tinnox browser` flow, in which the code step is `REQUIRED`; `npm run verify:oidc` proves a password-only user is sent to authenticator set-up and gets no code. The API still cannot verify MFA from claims with this realm; production start-up still requires ACR or AMR settings. |
| T12 | ID tokens carry no names (the client has no `profile` scope) and the stored copy is removed when the session ends. Audit `occurred_at` is set by the database on every insert. Rejected device credentials are audited per client address with a keyed fingerprint of the address, not per token. |
| T13 | Build-time sources were incomplete: ghcr.io (gitleaks image), the Alpine package repository (`ffmpeg`) and Playwright's browser download are now in the inventory (operations checklist section 4). |
| T15 | `TRUST_PROXY=true` made `request.ip` the client-chosen leftmost `X-Forwarded-For` entry, defeating every per-address limit. `TRUST_PROXY` now accepts only `false` or a list of proxy addresses and ranges; `true` and hop counts are refused at start-up (Fastify 5.12 ignores hop-count trust anyway). One shared, serial worker still lets one organisation's slow uploads time out another's (no per-organisation fairness; open). |
| T5 | The portal and player dev and preview servers now send `frame-ancestors 'none'`, `X-Frame-Options: DENY` and `nosniff`, so the portal cannot be framed in the documented run modes. Router-level refusals now use the standard envelope and headers. A production edge must send the same headers; no reference configuration ships yet. |
| T2, T4 | `publication_asset` rows can be added only in the transaction that created their publication and only as the manifest lists them, so an application bug cannot widen what a player may download from an existing publication. |
| T9 | A player whose IndexedDB connection is closed by another context or by the browser now reloads instead of playing stale content without updates, and opens a database left at a newer version by a later build instead of stopping with a fatal screen. Unit-tested against fake-indexeddb, not in a real browser. Player errors are dropped once a successful sync cycle has resolved them, so the portal no longer lists old delivery errors next to an in-sync summary (E2E 11). |

## 10. Stage B, slice 2: built-in apps (2026-11-16)

Apps (Clock, Date, Countdown, Ticker, QR code, Text) are drawn by `packages/app-render`, in the player and in the portal preview. Spec: `docs/portal-v2/stage-b.md`, slice 2.

| Threat | Change |
|---|---|
| T5 | Operator text in app settings (ticker text, labels, QR content and caption, heading, message) is validated by strict contracts (length, no control or text-direction characters, no lone surrogates) and drawn with `textContent` only; styles go through CSSOM `setProperty`, motion through the Web Animations API. A build check (`packages/app-render/src/build-checks.test.ts`) fails on `innerHTML`, `outerHTML`, `insertAdjacentHTML`, style attributes, `cssText`, `fetch(`, `XMLHttpRequest` and dynamic `import(`, and the browser ESLint rules apply to the package. Nothing is fetched: an app renders from the publication, the player's clock and the site's time zone. Residual: a QR code can encode any text, including a link to any site; what it points to is the operator's responsibility, and neither the portal nor the player checks it. |
| T13 | New run-time dependency `uqr` 0.1.3 (MIT, no dependencies), pinned exactly in `packages/app-render/package.json` with its lockfile integrity. It encodes QR codes in the player and in the portal (both bundle it; no network use). Residual: it is little maintained (no release between Aug 2023 and Apr 2026); `npm audit` covers only published advisories. |
| T2 | The new `app` table has forced row-level security and a tenant policy, organisation-scoped foreign keys from `playlist_item`, and no `UPDATE` grant on `type`, `org_id` or `id`. Publications hold a copy of the settings, so deleting an app never changes a publication. |

## 11. Stage B, slice 3: schedules (2026-11-17)

A schedule is a default playlist plus weekly events that name other playlists; a screen has a playlist or a schedule assigned. A push copies every playlist of the schedule into one immutable publication (manifest v4), and the player picks between them from its own corrected clock. Spec: `docs/portal-v2/stage-b.md`, slice 3. No new dependency, no new route outside the operator scope, no change to the player routes, the signed media URLs or the heartbeat.

| Threat | Change |
|---|---|
| T2, T5 | Schedules add no outside data: a schedule refers only to playlists of its own organisation, nothing is fetched, and no new content type reaches a screen. The two new tables, `schedule` and `schedule_event`, have forced row-level security and the tenant policy, organisation-scoped foreign keys (to `playlist`, and from `display.assigned_schedule_id`), no `UPDATE` grant on a schedule's `id` or `org_id`, and no `UPDATE` grant at all on `schedule_event`; the five `/api/schedules` routes sit behind the session, CSRF and exact-Origin checks like every operator route. A schedule's name and description are operator text: validated by the strict contracts (as playlist names are) and shown in the portal as text nodes only (React escaping; no `innerHTML`). They are not copied into the manifest, which holds no schedule or playlist name or id, so they never reach a player. Media of every playlist of a pushed schedule is authorised through the same `publication_asset` rows as before. Residual, availability only: a player build older than 0.4.0 that is sent a v4 manifest refuses it and then asks for the manifest and sends a heartbeat about every 2 seconds until its page is reloaded (both under the per-credential route limits); the release note says to reload screens first, and 0.4.0 no longer does this for a later version. |

## 12. Security review round 3 fixes (2026-11-17)

Findings and fixes: `docs/reviews/2026-11-17-security-round-3/` (section 11 there). Changes to the picture above:

| Threat | Change |
|---|---|
| T3 | An older claim that no player had collected could still complete after the display was re-paired or its player revoked, and then take the screen from the newer player without a revocation event. Now a newer claim of the display, or revoking its player, cancels every uncollected claim, and completion never replaces an active registration (migration 0010). The operator's five-wrong-codes budget is checked and used under a lock per operator, so concurrent claims cannot pass it. A polling-token lockout is audited (`pairing.lock`, unscoped) in the same transaction as the lock, and pairing creation in the same transaction as the session. |
| T1, T15 | The orphan sweep could delete the files of pending jobs beyond the first 500 in the queue, in any organisation. It now removes a file only when the complete pending list shows it has no owner, and removes nothing when that list may be cut off (5000 jobs or more). When the answer to a COMMIT is lost, upload bytes and stored media copies are kept rather than deleted. |
| T6, T10 | Rotating `SESSION_SECRET` never ended established sessions, although the runbook said it did. The runbook now says what it does (cancels sign-ins in progress) and gives a tested global sign-out (`scripts/revoke-all-sessions.sql`). |
| T2 | `tinnox_app` can change its own role defaults, including clearing its timeouts; PostgreSQL does not let that be revoked. The API sets its timeouts and `row_security=on` when it connects, so such a change does not reach it. |
